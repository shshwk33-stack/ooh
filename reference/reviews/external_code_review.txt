ZIP
ㄱㄱ
업로드하신 zip을 풀어서 구조부터 확인하고, 지시서·코드·테스트·결과를 대조하는 검수를 시작할게요.
지금 코드 핵심부(정차탐지·격자·점수화)를 읽는 중이고, 동시에 설치(uv sync)를 백그라운드로 돌리고 있어요. 다음은 실험/검증 코드(bootstrap·holdout·누수) → 테스트 실행 → 변이 테스트 순서로 진행해요.
테스트(38 passed, 1 xfailed)는 제 환경에서 보고서와 동일하게 재현됐어요. 지금은 "통과하는 테스트가 놓치는 오류"를 찾는 단계라서, 외부 parquet(시간단위 µs)·GPS 스파이크·노이즈 같은 현실적인 입력을 직접 넣어보고 있어요. 전체 연구 파이프라인 재실행도 백그라운드로 돌리는 중이에요.
중간 점검: 전체 연구 파이프라인을 처음부터 다시 돌렸더니 보고서의 합성 결과표 20개가 수치까지 완전히 같게 재현됐어요(재현성은 진짜). 반면 제가 직접 넣어본 입력에서 실제 버그 2건을 찾았어요. (1) 시간 단위가 µs인 외부 parquet을 넣으면 정차가 0개로 나오고 F1=0이 조용히 나옴, (2) GPS 점프 1개가 정차를 둘로 쪼개 방문 수를 부풀림. 이제 실데이터 다운로드 시도·앱 구동·원본 PoC 감사·변이 테스트로 넘어가요.
앱 서버(health/root 모두 HTTP 200)와 원본 노트북 깨끗한 커널 재실행(14/14 셀 성공)도 확인했어요. 실데이터 재다운로드는 이 환경의 네트워크 제한(ProxyError)으로 실패해서 LaDe/Amazon/OSM 재분석은 "미실행"으로 표시할게요. 이제 "일부러 코드를 망가뜨려도 테스트가 잡아내는지" 확인하는 변이 테스트 18개를 돌리는 중이에요(약 5분).
정직하게 만든 연구 시스템이고 재현성도 진짜입니다. 다만 외부 데이터로 쓰기엔 정차 탐지에 결함이 있고, 테스트가 통계 검증 부분을 지켜주지 못합니다. 학회에서 "이동정보가 도움이 된다"를 입증하는 논문으로는 아직 부족합니다.
미실행 항목
- 실데이터 재다운로드: LaDe·Amazon·OSM이 모두 네트워크 제한(ProxyError)으로 막혔습니다. 이 분석 결과는 제출된 표와 내부 일관성(합계·행 수)만 확인했고, 원본 대조는 못 했습니다.
- GitHub Actions 원격 실행.
- 원본 참고자료 4개의 바이트 일치 확인(원래 zip이 없습니다).
- git 이력 확인(zip에 .git이 없습니다).
P4가 부분충족인 이유는 다음과 같습니다.
- 동시간·동장소 공간 특성이 없습니다. 공간자료는 "기간 전체에 유효"라는 정보뿐이고 시간대별 인구가 없습니다.
- 공선성을 진단만 하고 해결하지 않았습니다(M1).
- "어떤 상황에서 이동정보가 유용한가" 분석이 사실상 없습니다.
섞이거나 위장한 흔적은 못 찾았습니다.
- 모든 표에 observation_type이 붙어 있고, 앱 화면에는 SYNTHETIC 경고가 뜹니다.
- 이벤트·방문지 자료를 GPS로 넣으면 코드가 거부합니다.
- 미국·중국·서울·합성 자료를 서로 결합하지 않았습니다.
- 광고효과와 정확도 향상 주장도 문서 곳곳에서 스스로 부정합니다.
과장에 가까운 부분은 두 가지입니다.
- 대표 수치 F1 0.9885는 가장 쉬운 조건(GPS 오차 5m, 정차 6분 이상)에서 나온 값입니다. 어려운 조건에서는 크게 떨어집니다(H2).
- "복수 seed 재현"은 seed를 바꿔도 시나리오가 바뀌지 않아서 검증력이 거의 없습니다(M3).
H1. 시간 단위가 µs인 parquet을 넣으면 정차가 0개, F1=0이 조용히 나옴
- 위치: stops.py::detect_stops의 ts = g.timestamp.astype("int64").to_numpy() / 1e9
- 근거: 시간 단위가 ns라고 가정한 코드입니다. Spark·DuckDB 등 외부에서 만든 parquet은 보통 µs이고, 이러면 시간이 1000배 작게 계산됩니다. 오류나 경고 없이 stops=0, F1=0.0이 나왔습니다.
- 재현: p2_us_unit_spike.py 실행. 현재 테스트는 이 경로를 전혀 검사하지 않습니다.
- 수정: ts = (g.timestamp - pd.Timestamp(0, tz="UTC")).dt.total_seconds().to_numpy()로 바꾸고, µs·ms parquet 회귀 테스트를 추가합니다. 유효 구간은 많은데 정차가 0개면 경고도 띄웁니다.
H2. 정차 탐지가 현실적인 GPS 노이즈에 약함
- 위치: stops.py::detect_stops. 첫 점을 기준점으로 고정하고 반경 30m 안에 있는 동안만 이어붙입니다.
- 근거: 제출된 robustness.csv를 보면 오차 5m(30초 주기)에서 F1 0.99이지만, 15m에서 0.22(120초 주기는 0.44), 35m에서 0입니다. 표본 주기 300초는 최대 연결 간격(180초)보다 길어서 항상 0입니다. 원본 PoC가 5분 주기였으니 새 엔진은 원본이 다루던 데이터조차 못 다룹니다.
- 수정: 기준점을 이동 중앙값으로 두고, 반경을 max(30, 2×accuracy)로 하며, 일시적 이탈 몇 점은 허용합니다. 최대 간격은 표본 주기의 3배 정도로 자동 설정합니다.
- 보고서가 실패 조건을 숨기지 않은 점은 인정합니다. 하지만 대표 수치가 쉬운 조건의 것이라는 점은 본문 첫머리에 명시해야 합니다.
H3. GPS 점프 1개가 정차를 둘로 쪼개고 방문 수를 부풀림
- 위치: quality.py::normalize_gps. 점프 판정이 "이후 점"에 걸려서 스파이크 1점이 2점을 무효화합니다.
- 근거: 정차 한가운데에 5km 스파이크 1점을 넣었더니 F1 1.0→0.77, 방문 수 6→7이 됐습니다. 무효 점은 2개(스파이크 + 멀쩡한 다음 점)였습니다.
- 재현: p3_spike.py
- 수정: 스파이크 점만 제거합니다. 그다음 이전 정상 점 대비 속도를 다시 계산합니다.
H4. 테스트가 통계·검증 로직의 오류를 못 잡음 (변이 테스트 20개 중 10개 생존)
- 못 잡은 변이: 
  - holdout에서 테스트 정규화를 다시 맞추는 데이터 누수 (M07)
  - bootstrap을 복원추출 없이 수행 (M08)
  - placebo의 순열 제거 (M09)
  - 강건성 비교 기준을 자기 자신으로 교체 (M13)
  - 정적 가중치 .7/.3 뒤바꿈 (M06)
  - 시간대를 UTC로 집계 (M10)
  - 공간 결측을 0으로 채움 (M11)
  - 정차 매칭 IoU 기준 변경 (M12)
  - 방문을 시간 구간별로 중복 계산 (M17)
  - 순위 방향 반전 (M18)
- 잡은 변이는 정차시간 계산, 시간대 변환, 좌표 투영, 격자, 점프·간격, 합성/실측 혼용 방지 등 기본 엔진 쪽입니다.
- 의미: “38 passed”가 안전하다는 뜻이 아닙니다. 특히 누수와 bootstrap이 깨져도 초록불이 켜집니다.
- 수정: 아래 테스트를 추가합니다. 
  - holdout이 train 정규화를 그대로 쓰는지 확인
  - bootstrap에서 중복 차량이 실제로 나오는지 확인
  - 강건성 baseline과 비교 대상이 다른 객체인지 확인
  - hour 값이 로컬 시각과 일치하는지 확인
  - 커버되지 않은 격자가 NaN으로 남는지 확인
- L1. features.py가 UTC 기준 floor("h")로 시간을 나눠서, 30분 단위 시차 지역(인도 등)에서는 시간대 귀속이 틀립니다. 한국은 정상입니다.
- L2. 격자 투영이 126°E 서쪽(인천 옹진 등)을 거부합니다. Grid.project는 EPSG:32652의 적용 범위 밖이면 예외를 냅니다. 또 시간대 없는 valid_from을 넣으면 ValueError가 아니라 TypeError가 나서 CLI가 잡지 못하고 트레이스백이 뜹니다.
- L3. 가중치 민감도의 “Top-K overlap 0.20–1.00” 범위에 자기 자신과 비교한 값(α=0.6 → 1.0)이 포함됩니다.
- L4. 테스트가 상대경로(Path("scripts/audit_legacy.py"))를 써서 프로젝트 루트에서만 돌아갑니다. 레거시 감사의 165분은 코드에 하드코딩된 상수입니다.
- L5. 그림이 어색합니다. 노이즈 히트맵은 왼쪽 여백이 크고 기여도 그림은 범례가 막대를 가립니다.
- L6. ruff는 E9/F만 통과시켰고, 기본 규칙으로는 38건이 나옵니다(대부분 스타일). CI의 uv 버전 0.12.19는 이 환경에서 확인하지 못했습니다.
- 누수: 코드상 실제 누수는 없습니다. holdout은 train 정규화를 test에 그대로 적용합니다. 다만 이를 지키는 테스트가 없습니다(H4).
- 순환성: 합성 공간필드와 이동 경로는 서로 독립으로 생성되어서 입력으로 정답을 만드는 구조는 아닙니다. 그런데 "정적 vs 통합 Spearman 0.40"은 통합점수가 정적 점수를 40% 포함하므로 구성상 달라질 수밖에 없는 값입니다. 문서에도 "정확도 증거 아님"이라고 쓰여 있습니다.
- 공유 성분 문제: holdout·robustness 일치도가 정적 점수를 공유해서 좋아 보입니다(M2).
- 정확도·광고효과 주장: 문서 어디에도 없고, 스스로 부정합니다.
제출을 막는 요인은 다음과 같습니다.
1. 실제 차량 GPS가 없습니다. 지금 결과는 "합성 데이터 스트레스 테스트 + 다른 나라의 이벤트 데이터 기술통계"입니다.
2. 이동정보가 후보지 판단에 도움이 된다는 증거가 없습니다. 독립적인 정답(전문가 평가, 노출 지표)이 없고, 비교 결과는 구성상 달라지는 값뿐입니다.
3. 선행연구 검토와 신규성 논증이 없습니다.
4. H2·H3 때문에 "정차 탐지 검증"이라는 핵심 기여가 쉬운 조건에서만 성립합니다.
현실적인 제출 방향은 "재현 가능한 분석·검증 프레임워크와 실패 조건 공개"입니다. 이 경우 필요한 작업은 다음과 같습니다.
- H1~H4 수정
- M3·M4 반영(여러 시나리오로 재실험, 짧은 정차와 긴 신호대기 추가)
- 실제 배송차량 GPS 확보(동의받은 소규모 자료라도)
- 선행연구 검토 작성
- 합성·실측 구분, 서로 다른 지역·시기 자료 결합 금지, 실패한 다운로드를 숨기지 않는 설계.
- 원본 PoC의 알려진 오류를 strict xfail로 보존한 것. 일반 실패와 구분됩니다.
- 시간 보존 테스트와 격자 경계 테스트.
- 나쁜 결과(F1 0.22, 300초 주기에서 탐지 0)도 그대로 공개한 것.
참고로 재현 스크립트 7개와 변이 테스트 20개 결과는 review_probes.zip에 담아 보냈습니다.
