# Transit OOH 3차 발표 대본

10장 / 약 9분 / 자료 확인 기준 2026.10.11

## 01. 이번 발표의 초점

안녕하십니까. Transit OOH 3차 진행 상황을 발표하겠습니다. 저희는 배송차량의 이동정보와 지역 특성을 함께 사용해, 어떤 장소를 우선 검토할지 돕는 분석 시스템을 만들고 있습니다. 이번 발표에서는 실제 데이터를 어디에서 구했고, 현재 어떤 파일을 확보했으며, 이를 처리할 프로그램을 어디까지 구현했는지 설명드리겠습니다. 오른쪽은 이번에 받은 마포구 도로망입니다. 차량이 실제 주행한 GPS 경로를 그린 것은 아닙니다.

근거: 공식 도로망 파일의 공급자 마포구 코드로 408개 링크를 추출. 자료의 정의와 제약은 VIEWT_COLLECTION_STATUS.md 및 network_validation_summary.json 참조.

## 02. 1·2차 발표와 이어지는 지점

1차 발표에서는 배송 과정에서 쌓이는 데이터를 새로운 의사결정에 활용할 수 있는지 질문했습니다. 2차 발표에서는 합성 GPS로 정차를 찾고 점수를 계산한 뒤 지도에 표현하는 초기 실험을 했습니다. 이번 3차는 그 구조에 실제 자료를 연결하기 위한 준비 단계입니다. 그래서 새로운 최종 성능을 제시하기보다, 공식 파일을 확보한 과정과 구현 현황을 보여드리겠습니다. 연구 질문은 그대로입니다. 이동정보를 공간정보에 더했을 때 후보지를 어떻게 다르게 검토할 수 있는지를 확인하는 것입니다.

근거: 기존 발표자료를 SOURCE_AUDIT.md와 대조. 현재 성과를 원본 2차 PoC에 소급하여 기재하지 않음.

## 03. 데이터를 확보한 방법

데이터는 한국교통연구원의 View-T 공식 사이트에서 확보했습니다. 먼저 자료 설명과 메뉴를 확인한 뒤 연도, 지역, 요일을 맞춰 파일을 받았습니다. 도로망과 행정경계는 지도 ZIP 파일로, 교통량과 평균속도는 Excel로 받았습니다. 도로 지표의 조건은 2024년 마포구 평일이고, 실제 파일에는 연평균 하루 값이 들어 있습니다. 인구 이동 분석은 별도 Expert 메뉴에서 마포구로 들어오는 조건을 설정했습니다. 다만 CSV를 받으려면 토큰키가 필요해서 현재는 다운로드 전 단계에서 멈춰 있습니다. API 자동 수집을 완료한 상태는 아닙니다.

근거: 공식 페이지 및 사용자 다운로드 원본의 조건 행 확인. 연평균 일 자료는 날짜별 원시 관측값이 아님. 인구 분석의 설정값은 데이터 확보를 뜻하지 않음.

## 04. 마포구를 기준으로 범위 설정

전국을 한꺼번에 분석하기보다 마포구 한 곳을 예시 지역으로 정했습니다. 지도는 실제 확보한 파일로 그렸고, 16개 동의 경계와 공급자가 마포구로 분류한 408개 도로 구간을 보여줍니다. 연구 대상은 여러 거점을 반복적으로 도는 밀크런형 배송차량입니다. 아래 연결 그림은 이 운행 방식을 설명하는 그림이며, 관측한 차량 경로는 아닙니다. 경계는 2023년, 도로는 2024년 자료라는 차이도 있습니다. 따라서 지금 지도는 자료 범위를 확인하는 용도로 사용하고, 동별 점수를 계산하기 전에 경계 버전이 일치하는지 확인하겠습니다.

근거: 마포구 도로 수는 지리적 클리핑 결과가 아니라 공급자 sigungu_id=11140 기준. 경계를 통과하는 모든 도로 수와 다를 수 있음. View-T 주요도로망은 모든 골목·배송 접근도로를 포함하지 않음.

## 05. 어디까지 확보했는가

현재 확보한 자료는 행정경계, 도로 네트워크, 추정교통량, 평균속도의 네 종류입니다. 교통량과 속도는 각각 마포구 408개 도로 구간에 대응합니다. 교통량에는 전체 차량과 승용차, 버스, 트럭이 나누어져 있습니다. 다만 이 값은 연평균 하루의 추정 통행량이고, 개별 차량을 추적한 기록은 아닙니다. 속도도 전체 차량의 평균이므로 배송차량의 정차시간으로 해석할 수 없습니다. 인구 CSV, 차량 대표 경로, 실제 배송 GPS와 분석 기간에 맞는 시설정보는 추가 확보가 필요합니다. 다른 공개 자료로 수행한 별도 분석을 마포구 자료로 섞어 넣지는 않았습니다.

근거: 교통량 대/일과 평균속도 km/h는 서로 다른 단위. POI는 시설·장소 정보이며 기존 서울 일부 OSM 자료와 동기간 마포구용 완전한 자료는 구분.

## 06. 파일을 검증한 방법

파일을 받았다고 바로 합치는 것은 아닙니다. 먼저 도로망, 교통량, 속도가 같은 도로를 가리키는지 도로 구간 번호로 대조했습니다. 세 자료에서 마포구 408개 번호가 모두 일치했고, 교통량과 속도 표에는 중복 번호나 누락된 셀이 없었습니다. 이는 파일을 서로 연결할 수 있는 기초 조건을 확인한 결과입니다. 추가로 위치를 표현하는 좌표 기준, 자료의 연도와 평일 조건, 교통량과 속도의 단위를 확인했습니다. 다만 현재 앱은 날짜별 표준 입력을 처리하므로, 이번 연평균 파일을 안전하게 연결하려면 집계 방식에 맞는 별도 변환 기능이 필요합니다.

근거: 정합성 검사는 로컬 업로드 파일에 한정. 2023년 경계와 2024년 도로 버전 동일성 검증 완료를 뜻하지 않음. XLSX A1:A1 잘못된 dimension은 reset_dimensions 후 전체 행을 확인. 소수점 형태 숫자 도로 ID는 정수성 확인 후 문자열로 처리.

## 07. 정보통신공학 관점의 구현

시스템은 크게 입력, 검사, 정보 추출, 결과 화면의 네 부분으로 나누었습니다. GPS가 들어오는 경로에서는 잘못된 위치와 긴 시간 공백을 확인하고, 이동시간과 정차시간, 방문 횟수를 계산합니다. 정차시간은 단순히 GPS 점 개수를 세는 방식 대신 관측 시각의 실제 차이를 사용합니다. 표 형태의 교통·인구 자료는 별도 경로에서 지역, 연도, 단위와 공간 번호를 확인합니다. 두 경로는 자료의 의미를 유지한 상태에서 점수 계산과 화면 출력으로 이어집니다. Python으로 계산하고 공간 처리 도구를 이용해 위치를 연결하며, Streamlit으로 사용자 화면을 구현했습니다. 현재 GPS 기능과 표준 파일 흐름은 합성 입력으로 시험했습니다.

근거: 분석 모듈: cleaning, stops, features, scoring, experiments, viewt. GPS 점수와 집계 통행량 점수는 별도 구현. 집계자료의 공식 연평균 어댑터는 미완료. 정차 목적이 배송인지 신호대기인지는 GPS만으로 확정 불가.

## 08. 점수와 가중치의 의미

최종 점수는 이동 점수와 공간 점수를 섞어서 계산합니다. 이동 점수는 GPS가 있을 때 이동시간, 정차시간, 방문 횟수를 사용합니다. 교통 집계자료를 쓰는 모드에서는 차량 통행량을 별도의 지표로 사용하며, GPS 지표와 같은 것으로 보지 않습니다. 공간 점수는 인구 통행 규모와 주변 시설정보를 반영합니다. 크기와 단위가 다른 값은 먼저 0에서 1 사이로 맞춥니다. 기본 비율은 이동과 공간을 반반 반영하는 50대50입니다. 사용자가 비중을 바꾸면 지도와 순위도 다시 계산됩니다. 공간만 보는 A, 이동만 보는 B, 함께 보는 C를 비교할 수 있습니다. 기존 60대40도 비교 대상인 초기 가정이며 최적값은 아닙니다.

근거: scoring.py: M=mean(z(moving_seconds),z(stop_seconds),z(visit_frequency)); S=.7z(population)+.3z(poi_count). viewt.py 집계 모드: M=z(vehicle_flow). I=alpha*M+(1-alpha)*S. 후보별 정규화 조건과 결측 검사는 구현 계약에 따름. 실제 마포구 점수 산출 완료를 의미하지 않음.

## 09. 대시보드에서 가능한 일

이 화면은 실제 실행한 웹 프로그램을 촬영한 것입니다. 화면에 보이는 후보 16개와 지도상의 순회선은 기능 확인을 위한 합성 데이터입니다. 앞에서 보여드린 마포구의 실제 16개 동 경계와는 구분해야 합니다. 사용자는 자치구와 입력 파일, 날짜와 시간대, 이동정보 비중을 선택할 수 있습니다. 결과 화면에서는 지도와 후보 순위, 상위 후보, 모델 비교와 가중치 변화에 따른 안정성을 확인하고 표를 저장할 수 있습니다. 기존 자동검사는 68개가 통과했고 실패는 없었습니다. 과거 코드의 알려진 오류 한 건은 예상 실패로 남겨 재현합니다. 이 검사는 프로그램의 처리 기능을 확인한 것이며 실제 광고효과를 검증한 수치는 아닙니다.

근거: 스크린샷: 실제 Chromium의 실행 화면, 합성 경고 유지, 외부 배경지도 미사용. reports/runs/tests.xml에서 tests=69, failures=0, errors=0, skipped=1(xfail). 합성 가중치 50→60 조작 시 결과 비율 변경도 브라우저에서 확인.

## 10. 다음 발표로 이어갈 계획

이번 단계의 성과는 네 종류의 공식 파일을 확보하고, 이 자료를 연결할 입력 조건을 확인했으며, 분석 기능과 사용자 화면을 구현했다는 점입니다. 다음 발표에서는 토큰과 인구 파일을 확보하고 공식 연평균 자료를 처리하는 변환 기능을 연결하겠습니다. 그다음에는 경로와 기간이 맞는 시설정보를 보강해 마포구 사례를 적용하고, 이후 모델과 가중치에 따라 후보 순위가 얼마나 달라지고 유지되는지 검토하겠습니다. 실제 배송 GPS가 없으면 가상 순회 시나리오라는 점을 명시하겠습니다. 발표가 세 번 남으면 비교·검증과 최종 시연을 묶고, 네 번 남으면 나누어 진행할 수 있습니다. 이상으로 3차 진행 보고를 마치겠습니다.

근거: 미래 계획이며 수행 결과가 아님. 인구 CSV 토큰 발급 및 데이터 제공 범위에 따라 일정 조정. 일별 원자료 없이 연평균 값을 복제해 일 단위 Bootstrap을 수행하지 않음. 순위 변화만으로 모델 성능 향상을 주장하지 않음.
